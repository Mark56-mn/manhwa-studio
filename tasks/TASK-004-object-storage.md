# TASK-004 — Object storage + assets (Phase B)

## 1. Objective

Give the studio real object storage so that generated media (and owner-uploaded
files) become durable, addressable artifacts. Add an `assets` table that records
every stored object's project/episode/type/storage-key/status/metadata, and a
real upload/read/delete path through the Cloudflare R2 bucket binding. Keep the
media-storage capability honest: it must never read `connected_verified` until a
real round-trip has actually been performed and recorded.

## 2. Current verified repository state (before this task)

- Phase A, TASK-002 and TASK-003 are complete. `npm run verify` = typecheck +
  lint + 100 specs (8 live skipped) + build, all green;
  `npm run verify:local` = 66 HTTP checks.
- `worker/env.ts` already declares `FILES?: R2Bucket`, but **no bucket is
  attached**: `wrangler.jsonc` has no `r2_buckets`, and `mediaStorageStatus`
  reports `not_configured` because nothing is bound.
- No `assets` table and no upload/read path exists. Nothing stores binaries.
- The capability vocabulary (`connected_verified`, `configured_unverified`,
  `unavailable`, `not_configured`, `failed`) and `provider_checks` already exist
  from TASK-002/003 and are reused here.

## 3. User-facing outcome

- On a project (and optionally an episode) the owner can **upload a file** and
  see the real asset listed with its kind, size, content type and time.
- An asset can be **opened** (streamed back from R2 with its stored
  content type) and **deleted** (the object and its row).
- Settings shows **Media storage (R2)** as `not_configured` when no bucket is
  attached, `configured_unverified` when one is, and `connected_verified` only
  after a real put/get/delete round-trip was performed and recorded.
- No binary is ever written to D1: the database holds metadata and the R2 key.

## 5. Required implementation

1. **A migration, not binaries.** `assets` records id, project, optional episode,
   kind, name, storage key, content type, byte size, checksum, status,
   provider/model, metadata JSON, owner and timestamps. Idempotent
   (`IF NOT EXISTS`), applied by wrangler or `POST /api/bootstrap`.
2. **A real bucket path.** `worker/storage/service.ts` writes through
   `env.FILES.put`, reads through `env.FILES.get`, and deletes through
   `env.FILES.delete`. The storage key is generated by the server
   (`projects/<projectId>/<kind>/<id>`); no user-supplied path is trusted.
3. **Server-side limits.** A maximum upload size, a content-type allow-list per
   kind, and a clear 4xx when either is violated.
4. **Ownership.** Every asset read/list/delete resolves the project from the
   signed-in subject; a foreign asset is a 404, never a leak.
5. **Honest capability.** `POST /api/storage/verify` performs a real
   put → get → compare → delete round-trip and records the result in
   `provider_checks` (`capability = 'media-storage'`). `mediaStorageStatus`
   derives its state from that row, exactly like the script capability.
6. **No regressions.** Existing specs stay green; the app still works with no
   bucket attached (uploads report `not_configured`).

## 6. Explicit non-goals

- Image/voice generation and video rendering (TASK-005/006/007): this task
  stores assets; it does not create them.
- Public/CDN delivery, signed URLs, thumbnails, virus scanning.
- Any change to the AI provider router (TASK-003) beyond capability reporting.

## 7. Acceptance criteria

1. `npm run typecheck`, `npm run lint`, `npm run build` pass.
2. `npm run test` passes, including new specs that upload real bytes into the
   workerd R2 binding, stream them back, list them, delete them, reject an
   unknown kind / disallowed content type / oversized file, enforce ownership
   isolation, and prove the capability only reaches `connected_verified` after a
   real recorded round-trip.
3. Existing specs stay green.
4. No secret is committed, logged or returned to the browser.
5. `npm run verify:local` passes and covers the new protected routes.
6. `POST /api/bootstrap` upgrades a Phase-B database by applying only
   `0004_assets.sql`.

## 9. Deployment or environment dependencies

- An R2 bucket bound to the Worker as `FILES`. Locally, `wrangler dev` provides
  it from `wrangler.jsonc`; in tests it comes from the miniflare R2 binding.
- For a prebuilt-Worker deployment the site must expose the same `FILES` R2
  binding. Without it the studio still runs and reports `not_configured`.
- No new secret variables are required.

## 10. Risks and fallback decisions

- **No bucket attached.** The upload path returns an honest 503 naming the
  missing binding instead of writing to the database only.
- **D1/R2 divergence.** The object is written first; if the metadata insert
  fails, the object is deleted again so no orphan is left behind.
- **Large files.** A hard size limit and streaming reads keep memory bounded.
- **User-controlled keys.** The storage key is server-generated, so a crafted
  filename cannot escape its project prefix.
